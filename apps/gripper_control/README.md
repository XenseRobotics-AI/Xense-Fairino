# TacCap / XTac 夹爪调试

运行 `bash run.sh console` →「夹爪调试」，或单独运行 `bash run.sh gripper`。
界面和机器人端控制实现共用，电脑负责显示，上半身通过已经安装的
`/home/fairino/umi/.venv/bin/python` 调用 main 分支引入的官方 TacCap SDK。
SDK 安装、设备供电/USB 与原始测试记录见 [umi 说明](../../umi/README.md)。

1. 填上半身 IP、用户和 SSH 密码，点击「扫描 / 连接（只读）」。
2. 默认按本机实际安装侧分配已知夹爪：机器人左爪 `TCGU01A28Z0018s`，
   机器人右爪 `TCGU01A28Z0015s`；其他设备保留 SDK 的 Left/Right 识别。
   只接入空闲的 Follower，显示固件 SN 与串口。可在连接前用固件 SN 明确覆盖左右；
   未知身份、重复身份不猜测，缺少的一侧保持灰色。
3. 设置电机力矩和速度，点击对应夹爪「使能 · 保持当前位置」。
4. 滑条只修改目标；点击「执行目标开度」「张开」或「闭合」才运动。
   0% 闭合、100% 张开，中间为连续开度。
5. 「暂停 / 保持」取消当前行程、保持位置；「下使能」或断开结束控制。

默认夹持力矩 **1.1 Nm**、电机轴速度 **0.25 rad/s**。力矩不是指尖力 N；
PICO 遥操另有可调速度，默认 **0.75 rad/s**，范围 0.01–1.0 rad/s；
工作台和命令行 `--gripper-speed-rad-s` 共用同一实现，手动调试默认值不变。
PICO 的夹持力矩自动取各爪电机持续堵转额定值与固件生效持续包络的较小值，
使能前重新读取并校验；当前两只 EL05 的最大持续设定仍是 **1.1 Nm**，与原固定值相同。
1.8 Nm 峰值包络不作为持续夹持目标；工作台运行反馈显示每只夹爪实际采用的力矩设定。
PICO 可分别设置左右最大开度百分比，`开度 = 上限 × (1 - Trigger)`；
上限只影响遥操映射，独立调试页仍使用 0–100% 全行程，设备标定不变。
上述安装侧绑定由调试页、独立程序、PICO 和模型实测开度共用。
SDK 的左右来自序列号末位奇偶，不能反映实际安装侧；2026-10-22 已按用户确认的
安装位置修正这两个 SN。PICO 原有手柄到机械臂的镜像规则保持不变：
操控某侧机械臂的手柄 Trigger 控制安装在该侧机械臂上的夹爪。
修改后需要断开夹爪调试或结束 PICO，再重新连接；已有会话不在运行中切换设备。
低力矩设置同时限制 SDK 的闭合端预压力，确保预压力不超过请求的夹持力矩。
每次使能前按实际电机规格和固件生效包络校验，使用官方 `ForcePositionController`，
先启动状态流并以当前位置播种，再使能。运动中只读取控制器 snapshot，
不额外轮询串口。没有自动清错、标定或固件配置写入。

夹爪与上半身关节分别持有控制权；夹爪调试和 PICO 夹爪控制互斥。
切换到 PICO 前，先在调试页点击「断开夹爪 · 下使能」并等待结束，再启动遥操。
远端另有进程锁与 SDK 串口独占。输入/反馈确认中断退出时请求下使能；
PICO 连续目标中断 0.25 秒先保持，随后连接超时退出。
夹爪使用独立的 SDK 指令协议，不等待机械臂的腕部保护握手。
使能、下使能、开度和保持指令超过 3 秒未确认，即使反馈仍在更新，也会报告具体
指令超时、结束会话并请求下使能；确认结束后可重新连接，不自动重新使能。

工作台机器人模型复用「夹爪调试」只读连接或 PICO 夹爪会话的实测 `position`，
不使用目标开度，也不另开串口。只需点击「扫描 / 连接（只读）」即可查看开度，
不用使能；切换 PICO 前先断开调试会话。无控制器时每 0.1 秒读取一次状态，
有控制器时直接读取 SDK 状态流，周期上报为 0.05 秒，PICO 到界面的显示回传为 0.1 秒。
每帧保留采样年龄与电脑接收时间，超过 0.5 秒变灰并保留最后位置。
夹指内部连杆只有单姿态 CAD，模型用两组刚性夹指近似开合；固定 TCP 不随开度变化。
仅连接工作台顶部的上半身 ROS 状态不包含夹爪开度，需上述夹爪会话提供。

连接后会显示使能前诊断，包括固件版本、故障有效标记、当前/历史故障及包络不匹配。
显示开度、温度说明已经连接，不代表使能检查通过。诊断使用缓存的只读结果，
控制器运行期间不额外轮询串口；点击使能仍会重新读取并复查，不自动清错或改包络。

2026-10-19 右爪 `TCGU01A28Z0018s` 的只读检查：固件 1.2.6，电机当前故障 0、
历史 `0x00000004`（SDK 故障表：欠压），诊断 flags 为 `0x15`，缺少固件 FwValid；
存储的持续/峰值包络为 1.1/2.0 Nm，SDK 给出的对应额定值为 1.1/1.8 Nm。
这几项会触发当前前置检查，程序尚未调用电机使能。历史欠压不代表此刻仍欠压；
缺少有效标记的固件故障字段不能当成已确认无故障。该次检查没有清错、运动或写入固件配置。

同日修复右爪后，已刷入仓库所附 1.2.16 镜像，断 24V 重新上电验证版本仍为
1.2.16，上电标定完成且 fail_reason 为 0，电机当前/历史故障均为 0；
持续/峰值包络已保存为 1.1/1.8 Nm，audit 通过。备份和实机记录在
`logs/20261019-right-gripper-repair/`，没有执行开闭目标。
修复共享检查与低力矩预压力后，已通过同一个 worker 实机验证：以 0.2 Nm
使能保持测量位置 0.8 秒，再下使能；最大归一化开度变化约 0.00031，
最终 status 为 0、下使能和会话清理均已确认。此测试不验证完整开闭行程或夹持能力。

这次实机复查发现共享程序对 `FwValid` 的理解有误：该镜像在 MCU 故障为零时也
返回 flags `0x15`（强制读取为 `0x17`）。已核对镜像 CRC32 `0x4A8CD360`、
SHA256 `ece89250246c85a6fb07d564772fb3312102748d60b85d1203a93dc3dc6c5067`：
0x52 命令处理函数在 `0x08018D1A`，报告构造函数在 `0x08021064`；
`0x08021146`/`0x08021148` 始终写入当前/历史 MCU 故障值，而
`0x080211E4` 的零值分支跳过 `FwValid` 置位。处理函数在控制错误或 deadline
历史非零时另外置位。因此该位缺失本身不能判定这个版本的零故障报告无效。

共享检查只对准确版本 `FirmwareVersion(1.2.16.0)`、报告版本 1、MIT 协议、
无 MCU 故障来源且 MCU 当前/历史值均为零的报告接受这种表示；其他版本和来源
保留严格检查。报告 Valid、电机 MotorValid、读取超时/部分报告、电机故障、
温度、位置和力矩包络仍参与使能检查。工作台、独立夹爪调试与 PICO 共用此实现，
重新扫描夹爪时将发送最新实现到上半身。

2026-10-20：最新目标传输周期调整为 10 ms，接收循环 10 ms，周期反馈 50 ms；
SDK 状态流仍为 100 Hz，目标超时保持和故障检查保持原值。
