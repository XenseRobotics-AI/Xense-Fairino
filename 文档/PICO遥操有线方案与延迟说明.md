## 3. 启动和操作

电脑已有依赖，先启动 PC Service；如果已经运行，不重复启动：

```bash
cd /home/lim/lerobot-xense
bash scripts/pico4/run.sh service
```

头显打开 XRoboToolkit，将 PC / Server IP 设为电脑当前有线局域网地址，本次为 `192.168.31.152`。连接应显示 `WORKING`，同时打开 `Controller Tracking` 和 `Send`。建议关闭用 A 键切换 Send 的选项，避免与冻结旋转冲突。

可先在另一终端检查手柄数据，这一步不连接机器人：

```bash
cd /home/lim/lerobot-xense
bash scripts/pico4/run.sh monitor --duration 10
```

退出 monitor 后，当前 450 Hz 遥操命令为：

```bash
cd /home/lim/lerobot-xense
bash scripts/pico4/run.sh fairino --execute \
  --mode mirror_same_direction --rotation-mode mirror \
  --hand-mapping crossed --freeze-buttons --sensitivity 0.25 \
  --interpolation-hz 450 --receiver-hz 500 \
  --interpolation-delay-ms 12
```

启动后会使能 J1–J20，并先让双臂回到配置中的 Home；Home 不是机械零位。J15–J20 保持启动时身体位置。Home 期间松开两侧 Grip，完成后握住相应 Grip 遥操。

| 参数 | 含义 |
|---|---|
| `--execute` | 进入真实机器人控制 |
| `--mode mirror_same_direction` | 当前面对面平移映射，采用已经确认的沿房间同一方向方式 |
| `--rotation-mode mirror` | 姿态变化采用镜像旋转映射 |
| `--hand-mapping crossed` | 右手柄控制机器人左臂，左手柄控制机器人右臂 |
| `--freeze-buttons` | 启用手柄位移 / 旋转冻结按键 |
| `--sensitivity 0.25` | 缩放相对位移和旋转变化；这是灵敏度，不是速度上限 |
| `--interpolation-hz 450` | TCP 采样、IK 和发送目标的计划频率，周期约 2.22 ms |
| `--receiver-hz 500` | 机器人接收处理的轮询设置；输入也可唤醒处理，不代表实际每秒必定处理 500 个目标 |
| `--interpolation-delay-ms 12` | 在电脑收到的数据历史中，采样当前时刻之前 12 ms 的 TCP 目标 |

不指定时，下发默认 90 Hz、接收默认 200 Hz。参数要求 `下发频率 ≤ 接收频率 ≤ 500 Hz`，所以只把下发改成 300 或 450、不改接收频率会报错。500 Hz 是当前程序依据底层配置设置的参数上限，不是完整链路吞吐量保证。

| 操作 | 功能 |
|---|---|
| 按住对应 Grip | 控制相应手臂；松开停止更新并保持 |
| 按住 A / X | 冻结旋转，只改变位置 |
| 按住 B / Y | 冻结位置，只改变旋转 |
| 同时按住两类冻结键 | 位置与旋转都保持，松开不补走 |
| 物理左手柄摇杆上 / 下 | 灵敏度增 / 减一档，当前档位为 0.25、0.5、1；切换后先松开两侧 Grip |
| 物理右手柄摇杆按压 | 回双臂 Home，再按中止；途中握任一 Grip 或按空格也可中止 |
| 物理左手柄摇杆按压 / 空格 | 暂停 |
| Esc / Ctrl+C | 退出并全部下使能 |

冻结键作用于该手柄映射到的手臂。左右摇杆的全局功能按物理手柄区分，不随 crossed 映射互换。

## 4. 指令与反馈分别走什么链路

```text
控制路径：
PICO 约 90 Hz 原始帧
 → PC Service → Python SDK
 → 相对 TCP 映射、灵敏度、冻结
 → 12 ms 历史缓冲，按 450 Hz 采样：位移线性插值 / 姿态 SLERP
 → 每个采样点调用厂家 IK，并做本地校验
 → SSH / JSON
 → 上半身接收程序，保留最新待处理目标
 → 机器人端校验 → 发布 ROS 单点关节位置
 → 控制器 / 硬件 / 电机

反馈路径：
机器人硬件状态话题（本次观察约 47 Hz）
 → 上半身程序保存最新状态和命令计时信息
 → 约 100 Hz 回传电脑
 → 状态显示、保护检查、日志
```

现在遥操是**先对 TCP 插值，再解 IK**。IK 使用上一规划关节解作为参考，减少因反馈滞后产生的解分支变化，但不能保证经过奇异点时仍连续。

机器人端额外的 30 ms 关节追赶段已经删除。当前 ROS 轨迹消息只有一个位置点，`time_from_start=0`，消息头时间戳为 0；控制器采纳后保持这个点，直到下一点到来。使用机器人实际安装的 JTC 库进行的独立采样测试确认了这一点。这不等于电机能瞬间到达目标，也不排除驱动内部仍有控制和滤波。

Home 仍使用原来的关节空间五次时间曲线，和上述实时遥操 TCP 插值是两套逻辑。

12 ms 缓冲是为获得采样时刻两侧的已接收帧。没有后一帧时保持最新目标，不预测未来。即使输出也设为 90 Hz，只要采样时刻落在两帧之间，仍会插值。450 Hz 增加中间采样点，不会把 PICO 的真实信息量提高到 450 Hz。Grip 和冻结按键不等待这段插值缓冲。

电脑发送频率高于机器人处理频率，可能是线程调度、校验耗时及到达抖动共同造成的。接收程序会让最新待处理目标覆盖旧目标，避免积压后继续执行过时动作；因此“未逐帧处理”不等同于 TCP 网络丢包。真实接收频率应看日志，不能直接用 `--receiver-hz` 代替。

PICO 数据来自 `20261010-163556` 的 25 秒独立测量，接收约 90 Hz。当时 PC Service 端点为 `.31.32`，是在头显改为连接 `.31.152` 之前测的，**不能把 9.41 ms 当成当前新接收路径已复测的结果**。它不包含头显时间戳之前的内部追踪 / 预测耗时。

刚才实机日志中的“自电脑收到 PICO 回调后的样本年龄”中位数为 5.47 ms、P95 为 11.87 ms。这表示电脑正在使用的数据距离最近接收已过去多久，**不是 PICO 到电脑的网络单程延迟**。

反馈支路的 4.22 ms 等待不是每次电机动作前必须额外等待的时间。机器人可以先发布目标，之后才回传状态。实机只有约 100 Hz 的最新命令计时回传，不能完整覆盖约 450 Hz 的每个发送目标；实机观察到的确认 RTT 属于有选择的样本，因此不把它当作无偏的全量链路结果。

90 Hz 的周期约 11.11 ms，450 Hz 的周期约 2.22 ms，100 Hz 的周期为 10 ms。这些是更新间隔，不等于对应模块的执行耗时。约 47 Hz 是本次状态话题的观察频率，不是电机伺服频率。

目前可量化的主要部分是 PICO 输入传输、12 ms 设计缓冲、PC 求解、电脑—机器人传输以及机器人发布之前的处理；还不能给出精确的“手柄实际运动 → 机械臂实际运动”总延迟。往返不能直接除以二当作实测单程，各段中位数 / P95 也不能简单相加。

## 8. 后续如何复测

检查实际路由后，可用下列命令测电脑—机器人链路。此模式不使能、不发布运动目标，`--observe-ros` 只订阅状态：

```bash
cd /home/lim/lerobot-xense
bash scripts/pico4/run.sh fairino --link-check --observe-ros \
  --duration 12 --interpolation-hz 450 --receiver-hz 500
```

此测试出现被覆盖目标时可能返回非零退出码，需结合生成 JSON 中的处理数、间隔和 `errors` 判断，不能仅凭退出码认定硬件报错。

单独复测 PICO 当前接收路径，需要头显打开 Send，并通过 USB 供 ADB 查询时钟偏移。程序估计两端时钟差，不修改设备时钟：

```bash
cd /home/lim/lerobot-xense
bash scripts/pico4/run.sh latency --duration 25
```

无线输入仍可能出现间隔过长或恢复后的数据集中到达。有线不能消除 PICO 本身的 Wi-Fi 波动，12 ms 缓冲也不能填补任意长的缺帧。当前保持最新值、恢复后重新采样的行为，以及 J16 / J17 保持关节保护，是需要继续分别分析的问题，不能只提高频率解决。
