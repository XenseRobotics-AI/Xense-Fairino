# 开机检查与故障排查

在仓库根目录执行。开机/重启后可能出现全局 `0x0E10FF01`、各轴错误码 `30`，如 `J15=30`。现有故障表归为驱动器 EtherCAT 通信类故障，具体原因按当次反馈与日志判断。

项目内 [真实历史样例](../data/diagnostics/startup-fault30-reset.json) 记录了单次复位后故障归零且仍未使能。EtherCAT 从站达到 OP 通信状态与错误寄存器归零是不同状态。

```bash
bash run.sh errors
# 有故障时：退出控制程序，确认静止、急停释放
bash run.sh errors --execute
bash run.sh errors
```

默认先上半身后底盘，每块板至多请求一次 `reseterror()`。先复查总故障和关节故障归零，再按需请求一次 `disable()`；最终观察 5 秒，末尾至少 2 秒故障为零、静止且全部下使能才确认成功。清错不发送使能、Home 或运动目标。无故障但仍使能时只执行下使能，不发送复位。

B 原配置会在开机时自动激活 `eight_dof_chassis_controller`；统一配置迁移关闭了整套开机自动命令，需要重启机器人后生效。底盘 `--execute` 会在确认静止、速度指令近零、控制锁空闲及急停转发正常后，停用这个已知控制器并暂停里程计。控制器保持停用；其他运动控制器仍会阻止清错。上半身和底盘均允许部分轴仍使能，不再以先下使能作为复位前提。

当前安装的厂家库中，`disable()` 会检查硬件故障，`reseterror()` 入口则没有先全部下使能的要求。因此脚本顺序为“停止运动控制 → 确认静止与急停释放 → 单次复位 → 故障归零 → 下使能 → 最终复查”。复位不保证正常轴同时下使能，不能仅凭控制器已停用或故障归零认定电机已下使能。

清错的实测速度静止阈值为各轴绝对值不超过 **0.05 rad/s**；速度指令仍要求绝对值不超过 **0.005 rad/s**。2026-10-20 按用户要求放宽实测速度容差，以容纳当次静止采集中 J8 的约 0.012658 rad/s 离散读数；不放宽非零速度指令检查。前置观察约 0.5 秒，超限会显示关节和对应阈值。快停、未知/未就绪驱动状态、FATAL 故障、急停或反馈异常仍阻止复位。界面和命令行共用结果说明，区分前置检查失败、复位是否发送、故障复查、下使能和最终复查；失败时保留最后收到的反馈，不自动重试。

```bash
bash run.sh errors --part upper --execute
bash run.sh errors --part base --execute
```

| 问题 | 处理 |
|---|---|
| 控制锁或其他运动控制器占用 | 正常退出相应控制程序，再只读检查 |
| 开机底盘控制器仍激活 | 底盘 `--execute` 会先停用并复查 |
| 清错后下使能返回 `0xC012` | 检查是否故障复发或硬件状态异常；复位可能已经执行，不能再次盲目清错 |
| 上次键控临时控制器未卸载 | 先完成清错并确认全部下使能；新版底盘启动会在控制锁空闲、反馈正常、静止且输入回中后回收已停用的临时控制器，再按原流程回正使能。活动控制器仍拒绝自动回收；`--check` 始终只读 |
| 部分轴仍使能 | 停稳且满足前置检查后可单次清错，再下使能；以最终反馈确认完成 |
| 速度反馈未满足静止条件 | 核对提示的关节和数值；前置阶段超限不会发送复位，执行中出现则按报告确认复位是否已经发送 |
| 急停/上下板转发异常 | 检查按钮、上半身状态及转发 |
| 反馈超时 | 检查网络、服务和反馈链路 |
| 命令成功但故障未归零 | 以复查反馈为准 |
| 复发或 FATAL 故障 | 保存日志排查底层原因，不循环复位 |
| SSH 超时或清错中断 | 先只读检查，不自动重试 |

记录写入 `scripts/pico4/fairino/diagnostics/*-fault-reset/`。代码：[清错入口](../scripts/pico4/fairino/clear_errors.py)、[机器人后端](../scripts/pico4/fairino/fault_reset_remote.py)。

2026-10-22 的底盘退出样例：09:31:50 因 `J6=5` 故障停止，厂家 `disable()` 返回 `0xC012`，未确认全部下使能，因此跳过卸载临时回正控制器。09:43 清错及下使能成功后，旧启动逻辑仍被该 `inactive` 对象拦住。现在由键控与 PICO 共用的底盘后端在下一次启动时检查恢复；不自动复位错误。退出时若跳过卸载、卸载失败或复查仍有对象，`cleanup_confirmed=false`，日志附带 `remaining_controllers`；恢复过程记录候选状态、卸载结果和最终控制器列表。

## 工作台能连接 SSH，但上半身一直等待硬件反馈

2026-10-20 实测：上半身 `fairino_start.service` 正常运行；同一时段订阅 `/hardware_states` 6 秒，取消 Fast DDS 配置时收到 0 条，使用已有 `/home/fairino/fastrtps_udp.xml` 时收到 286 条，20 个关节数组完整。SSH 或 ping 成功只说明主机可达，不能证明 ROS 状态订阅已收到数据。

工作台旧反馈入口取消了 `FASTRTPS_DEFAULT_PROFILES_FILE`，与上半身键控、PICO 使用的 UDP 配置不一致。现由 `tools/ros_environment.py` 统一工作台和独立状态检查的环境：上半身使用 Domain 0 和上述 UDP 文件；底盘保留已验证的 Domain 1 配置。未修改机器人服务或控制器。具体默认传输失败的底层机制尚未进一步确定。

## 建图很快因位置不确定度过大而暂停

2026-10-17 的第二次建图：19:48:13 底盘就绪，19:48:25 启动建图服务，19:48:35 日志记录“滤波位置不确定度过大”并暂停，19:48:45 才开始键控移动。19:50:37 自动归档成功，但后续移动未加入地图。证据保存在 `logs/20261017-195225-map-review/`，包括实际 EKF YAML、机器人安装源码及建图日志。

触发者是本项目 `map_control_remote.guard_reason()`，条件为 `max(Pxx, Pyy) > 1`（单位 m²），不是厂家电机故障或 EKF 节点自行报错。当前 EKF 的 `odom0_config` 仅选择 vx、vy、yaw 角速度；x、y、yaw 位姿未融合，`imu0_config` 全为 false。位置由速度积分，不存在绝对位置观测来约束累计误差。

机器人安装源码的预测公式为 `P = J P Jᵀ + Δt Q`。实际 YAML 的 `Qxx=Qyy=0.05`，未启用动态过程噪声（该版本默认 false）。在静止、只融合速度的情形，固定位置噪声本身约累积 `0.05 × 秒数` m²；约 20 秒达到 1 m²。这里是过程噪声项的计算，不是实测位置误差，也不代表机体移动了 1 米。最后一帧记录到的 x 方差为约 7.94 m²。官方 [参数说明](https://github.com/cra-ros-pkg/robot_localization/blob/humble-devel/doc/state_estimation_nodes.rst) 也说明：仅融合速度时，位姿协方差会增长；动态过程噪声可用于抑制静止时的增长。

因此这个固定阈值与当时的轮速积分模式不匹配。2026-10-18 按用户要求改用原始轮速模式：`eight_dof_chassis_controller/odom → odom_guard（直通 /odom 与平面 TF）→ SLAM`，不再运行 EKF；原始模式不使用 `1 m²` 阈值。保留轮速和输出新鲜度、原始时间戳、有限值、硬件故障、TF 及里程计会话连续性检查。`/odom` 这个话题名现在并不代表它经过滤波，界面会明确标注来源。

后续如恢复 EKF 模式再评估动态过程噪声和实际传感器噪声标定，不能仅为消除提示而把协方差调小，也不应把同一编码器计算的位置和速度当成独立信息重复融合。原始里程计也会因轮径误差、打滑和转向误差漂移，雷达 SLAM 的匹配与闭环质量仍需实测。

## 雷达和 TF 在刷新，但运动时地图位置不对

2026-10-18 20:03–20:08 的两次地图存档分别仅接纳 3 帧、1 帧扫描。第二次在前后移动及连续转动期间没有接纳首帧以后的扫描。机器人 SLAM Toolbox 2.6.10 的 `shouldProcessScan` 先按平移筛选，忽略原地旋转，并在后端接纳之前就推进前端参考位置；与后端距离筛选叠加时，小范围往返也可能无新关键帧。隔离 Domain 197 中已复现原参数前进 0.75 米、返回、再旋转仍只有首帧。

修复保留前端时间节流，把运动取帧统一交给 Karto 后端依据上一已接纳帧判断平移或转角。独立程序使用相同 2.6.10 SDK，不改底盘和里程计；专用参数默认平移 0.10 米、转角 5°、地图发布 1 秒。静止不重复加帧，界面依据 SLAM `/pose` 显示最近匹配，不能把重复发布 `/map` 或 TF 的新时间戳当成新匹配。部署入口为 `tools/install_mapping_runtime.py --execute`，需隔离验证通过，下一次新建图使用修复版本。

诊断依据在 `logs/20261018-tf-review/`；修复构建与测试在 `logs/20261018-mapping-repair/`。此前 1 米测试只核对编码器距离，横移、转向、轮胎打滑与雷达外参仍需实机对照。可用 `tools/record_odometry.py` 同时保存两级 TF、两路里程计与成功匹配，再分析偏差发生在哪一级。
