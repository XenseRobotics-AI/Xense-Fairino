# 连接、故障和导航停止排查

## 一键恢复底盘接入

出现“上次控制器未卸载”“底盘故障未消除”“未确认底盘下使能”时，可点击地图窗口导航控制区的 **恢复底盘接入**。建图中先保存地图。按钮会结束本窗口的建图/导航底盘会话并等待真实退出，等待已有导航请求结束，然后执行一次恢复。恢复期间不能重新接入底盘；旧目标和预览会清除。

机器人端先取得与底盘控制相同的独占锁，确认新鲜硬件反馈、上身急停联锁和连续静止，再停止本工具管理的导航服务、暂停里程计、停用已知运动控制器。必要时只发送一次底盘故障复位，确认故障归零后按需下使能；持续确认八轴下使能后，卸载遗留的 `fairino_keyboard_angle` / `fairino_keyboard_chassis` 临时控制器。厂家控制器只停用、不卸载。

命令行入口从控制电脑的仓库根目录运行：

```bash
# 只读检查，不停止服务、不清错、不下使能、不卸载
conda run --no-capture-output -n env_fairino bash scripts/run.sh recover

# 先正常结束其他底盘控制会话，再显式执行一次恢复
conda run --no-capture-output -n env_fairino bash scripts/run.sh recover --execute
```

成功表示当前故障已归零、底盘静止、八轴已下使能且遗留临时控制器已清除。随后手动重新接入底盘，按提示重新初始化定位，再启动导航并发送新目标。恢复不会使能、回正、重启底盘或继续旧目标；它也不自动处理上身板故障。

下列情况会明确报告失败：原控制会话仍持有锁、硬件反馈过期、急停/上身联锁异常、仍在运动、不可复位的故障、未知运动控制器、里程计暂停未确认、下使能未确认等。不会删除锁文件、杀死其他控制会话或强行解除保护。故障持续存在时，仍需按故障信息检查硬件。SSH 断开或动作结果不确定时不自动重试，先用 `recover` 只读复查。

每次检查/恢复的阶段、动作和结果保存到 `logs/recovery/<时间>/result.json`；界面也显示失败原因和日志目录。新恢复程序随每次 SSH 请求发送，不依赖完整重部署导航；更新电脑端代码后，退出旧面板并重新打开即可出现按钮。使用的机器人 ROS、消息包、里程计守护和指令控制器仍须已正确部署。

## 故障处理

```bash
bash scripts/run.sh faults
# 先结束建图/导航底盘控制，确认静止及急停已释放
bash scripts/run.sh faults --execute
bash scripts/run.sh faults
```

默认先处理上身再处理底盘。上身故障处理保留，是因为底盘依赖上身急停转发；没有迁入上身运动控制。

执行流程保留原实现：确认运动控制停止和机器人静止 → 必要时至多一次 reseterror → 复查故障归零 → 按需 disable → 最终复查。清错不会使能、回 Home 或恢复运动。不能用“命令成功”替代硬件反馈确认。

| 现象 | 检查方向 |
|---|---|
| 控制锁被占用 | 正常退出原控制会话，等待清理完成；建图键控与导航互斥 |
| `0x0E10FF01`、轴错误 30 | 历史上属于驱动/EtherCAT 通信类故障；保存当次状态后按厂家故障定义处理 |
| 下使能返回 `0xC012` | 可能仍有硬件故障；检查复位是否已发生，不自动重复复位 |
| 上身急停反馈过期 | 检查上身板状态、急停按钮与转发服务 |
| SSH 断开或复位结果不确定 | 先只读检查当前反馈，避免重发动作 |

故障日志在 `logs/faults/`。`--part upper` 或 `--part base` 可限定检查板卡，具体参数以 `faults --help` 为准。

## 里程计或建图暂停

先查看原始 `/eight_dof_chassis_controller/odom`、输出 `/odom` 和 `odom → base_footprint` 是否新鲜。输入异常后守护程序锁定停止，健康数据恢复不会自动重启旧会话。

原始模式不经过 EKF，也不应用旧 EKF 的位置方差 1 m² 暂停阈值。旧 EKF 只融合速度时，位姿协方差可能持续增长；不要仅为去掉提示而调小协方差。

重新接入底盘可能改变里程计 epoch。旧建图不能直接继续；先另存并结束。已有地图定位也必须重新初始化。

## 地图/TF 在刷新但匹配未更新

检查界面的 SLAM `/pose` 成功匹配时间，而不是仅看 `/map` 或 TF 发布时间。固定选帧补丁允许转动约 5°或平移约 10 cm 后接纳新帧；静止时等待关键帧是正常状态。没有部署经过验证的独立 SLAM 修复版本时，管理程序会明确拒绝新建图。

## 导航走一小段停止

查看导航状态的 `failure` 和服务日志中的首个保护停止原因。当前速度流超过 0.6 秒未更新、定位/里程计会话变化、双雷达断流等都会锁定当前目标。恢复输入不会自动重发目标。

历史记录中曾有计算负载和 SSH nice 优先级异常。`deploy priority` 显示原有 PAM 修复；执行后只影响新会话，不能将它当作所有卡顿的通用修复。诊断需要区分指令断流、定位失效、网络延迟和舵轮响应。

最后一轮 10 Hz / LimitedAccelGenerator 调整的历史记录标注未部署、未实车验证。此次迁移没有改变这些事实，详见 [迁移验证记录](../reports/migration_20261104/validation.md)。

## 底盘协调反馈未就绪或等待超时

若显示“底盘协调尚未就绪”，查看导航状态中的 `chassis_motion.reason`。完整更新导航后还需退出并重新打开电脑端面板，重新接入导航底盘，才能加载新的 Worker 反馈发布器。准备导航节点阶段不要求这一路反馈；激活导航、预览和发送目标前要求反馈健康。反馈话题为 `/fairino_navigation/chassis_motion_state`，正常仅由本次 `fairino_keyboard_guard` 发布，空闲时也持续报告就绪状态。

`drive_wait` 表示观察到有运动请求但四个行走驱动器速度指令为零，并非厂商内部状态的直接回读。连续等待超过 `FollowPath.coordination_wait_timeout`（当前 15 秒）会停止目标；重规划、反复收到相同反馈不会重置等待预算。若 Worker 会话变化，应先结束并重新启动导航；不要通过重发旧反馈或自动恢复旧目标绕过保护。反馈过期门限沿用 `chassis.yaml` 的 `timeouts.feedback`（当前 0.4 秒），与 0.6 秒导航速度指令断流门限、1 秒定位 TF 门限不同。

协调层只处理等待期间的小非零意图和恢复后的加速，不消除驱动器自身故障。需要区分“底盘协调等待超时”与硬件状态错误；后者仍检查已有故障记录，不自动清故障或重新使能。

## 预览路径要求 --yaw，但界面显示保持当前朝向

如果远端报 `navigation_remote.py: error: plan/goal requires finite --x --y --yaw`，机器人执行的是仍要求手工朝向的旧版导航入口。在 `hold_initial` 策略下，新版电脑发送目标 X/Y 及预期策略，机器人端应在请求时读取新鲜 TF 锁定朝向；电脑源码更新或启动已有导航服务不会自动部署新程序。

先在界面结束导航并确认底盘下使能，再退出面板。检查 `config/navigation.yaml` 中 `nav2.controller_server.ros__parameters.controller_frequency`，当前预瞄控制配置为 `3.0` Hz；`1` Hz 会超过 0.6 秒速度超时，被配置检查拒绝。这里控制的是连续速度更新，降低到 1 Hz 不能实现平滑运动。

在控制电脑仓库根目录、已激活项目环境后执行：

```bash
bash scripts/run.sh check
bash scripts/run.sh deploy navigation --execute
```

检查通过后再部署。完整导航部署会编译并验证自有预瞄插件，然后更新机器人端脚本、Nav2 参数和启动环境；导航服务正在运行时拒绝更新。部署成功后重新打开面板，按原流程接入、定位、启动导航并预览路径。

不要为绕过这个旧版报错临时补 `--yaw 0` 或只复制 `navigation_remote.py`：这样不能保证保持真实当前朝向，也不能让旧 DWB 运行时变成预瞄控制器。预览出现本错误时尚未提交规划动作；客户端不会自动重试。

## 朝向策略不一致或缺少目标朝向

`path_tangent` 要求有限的目标朝向：GUI 使用度，CLI `--yaw` 使用弧度，均相对于 map 坐标系。输入为空或非有限数值时拒绝发送。`hold_initial` 仍显示“保持当前”并忽略旧接口中的手工 yaw。

若提示“朝向策略不一致”，核对电脑配置中的 `FollowPath.heading_mode` 与机器人已部署的策略；编辑电脑 YAML 不会更新机器人服务。结束导航、完整部署后重新打开面板。若旧机器人报 `unrecognized arguments: --heading-mode`，同样需要完整更新；客户端不会去掉该参数重试，避免把用户终点朝向静默当成保持当前朝向。

## 预览无法取得新鲜定位 TF

旧提示“无法锁定当前朝向：当前定位 TF 已过期或早于本次初始化”合并了不同原因，不能据此直接认定需要重新初始化。导航门控与预览命令原来使用不同的 TF 接收方式；命令在同步服务/文件检查后每轮只处理一次回调，可能在门控已经就绪时仍从自己的队列读到旧数据。

请求端现与门控共享独立 TF 接收器，状态查询期间持续接收，并在最后检查后重新获取位姿。TF 新鲜度仍严格小于 1 秒，未来时间偏差仍最多 0.05 秒，时间戳仍不能早于当前初始化；不靠放宽门限处理接收积压。过期、超前、初始化前数据及非法时间会分别报告时间差或时间戳。真实雷达/里程计断流、会话变化或线程故障仍会阻止发送目标。

此修复需要完整部署导航（包含共享 `tf_receiver.py`），不能只替换单个命令脚本。仅更新开发仓库不会改变机器人正在运行的程序。

## 定位匹配与 TF 保护

定位新鲜度按 AMCL 的更新条件判断：相对上次匹配对应的里程计基准，X 或 Y 的净位移严格大于 `update_min_d`，或最短净转角严格大于 `update_min_a`。这与累计路程不同；斜向走 0.1 m 不代表 X/Y 任一轴已经达到 0.1 m。

达到更新条件后，监视器最多等待 2 秒的新匹配，静止等待的时间不计入这段期限。里程计保留有界时间历史，按 AMCL 消息时间插值基准；迟到匹配按历史重建越阈时间，不能通过接收旧消息反复重开等待窗口。历史之外的后续旧匹配不重置保护；首次收到过旧的静止保留样本时只能从开始观察的里程计建立基准，状态以 `baseline_covered=false` 明示这一限制。

独立累计运动上限仍存在：平移为 `max(3 × √2 × update_min_d, 0.3 m)`，旋转为 `max(3 × update_min_a, 15°)`。它用于防止小范围往返或绕行一直不产生新匹配。超过等待期限或累计上限仍会停止目标；旧目标不会因输入恢复自动继续。

`Localization.start()` 将实际下发的 AMCL 更新阈值记录到定位会话，监视器使用该快照。旧会话没有快照时按原默认值 0.1 m / 5° 兼容；更新后应结束并重新启动定位，重新设置初始位姿。无效阈值、心跳时间、话题年龄或明显时钟回退不会判为就绪。

导航 TF 现在要求组合 `map → base_footprint` 的时间差绝对值严格小于 1.0 秒，且不早于本次初始化。此门限按用户要求由 0.5 秒调整为 1.0 秒，并由 `navigation/runtime_policy.py` 统一提供。新版错误区分查询异常、过期、时间超前和初始化以前的 TF；状态及保护停止日志新增：

- `tf.transforms`：`map_base`、`map_odom`、`odom_base` 的时间戳、年龄和查询异常。
- `localization_health`：匹配年龄、净位移、累计运动量、等待时间、阈值和基准覆盖情况。

AMCL 单独的 `map → odom` 可能带有 `transform_tolerance` 的未来时间量，它是诊断信息；是否放行仍由组合 TF 判断。仅有“TF 已过期”旧提示时不能断言哪一段断流，应读取上述分段数据。地图显示层与导航门限不同，地图能显示也不保证当前可以导航。

这项修复需要更新 mapping 的定位会话代码和 navigation 的监视器，然后重启面板与定位会话。导航门控优先加载其自身部署目录的监视器，避免被旧 mapping 副本遮蔽。更新代码、离线测试和实际部署是不同步骤；在机器人未部署之前仍运行旧逻辑。

## 导航反复报告 TF 过期

先区分数据发布延迟与导航进程接收积压。只看导航状态里的 TF 年龄不能区分这两种情况；应在机器人上用只订阅的独立节点，同时记录原始里程计、/odom、TF 接收时间以及导航状态。不要用电脑与机器人两台机器的墙钟直接相减。

2026-11-05 11:17（北京时间）的静止采样持续 30 秒：独立节点读到组合 TF 的年龄中位数约 0.035 秒、最大约 0.157 秒，而同一导航进程的 129 条不同状态中，12 条超过 0.5 秒。对齐门控实际检查时间后，一次门控记录 0.825 秒时，独立节点已经收到年龄约 0.025 秒的里程计 TF。这组证据将该次故障定位到导航进程的 TF 接收/处理积压；不是仅由界面旧提示造成。

门控使用独立的 TF 接收节点和执行线程，TF 历史及 QoS 保持原设定；速度命令、定位监视器与生命周期操作仍在原控制线程中串行处理。输出前重新查询 TF，并在同步工作完成后取当前时钟计算年龄。日志输出安排在速度发布之后。组合 TF 门限随后按用户要求调整为 1.0 秒；速度指令断流门限随后调整为 0.6 秒，双雷达门限为 0.5 秒。

状态与首次保护停止日志中的 `timing` 用于进一步定位阻塞：

- `tick_to_publish_seconds`：本轮开始到发布速度的处理耗时。
- `previous_tick_seconds`：上一轮完整处理耗时，含状态写入与日志。
- `last_graph_seconds`、`lifecycle_seconds`：图查询和生命周期处理耗时。
- `sample_ros_time`、`sample_monotonic`：最终健康检查使用的时钟。

`tf_receiver.running` 和 `tf_receiver.error` 记录独立接收线程状态。线程异常不会刷新旧 TF 的时间戳；没有新数据时仍按原新鲜度门限停止。

独立接收不能消除系统调度阻塞，也不会放行控制线程中已经过期的速度、里程计或雷达输入。开发仓库的离线测试通过后，还需要在机器人更新导航程序并重新进行静止采样，才能确认现场改善；不能把代码修改视为已经部署或实车验证。


### 导航提示里程计数据年龄超过 0.75 秒

先看机器人导航状态或保护停止事件中的 `topic_ages./odom`：
`received_age` 是距最近回调的时间，`stamp_age_at_receive` 是消息到达回调时已存在的延迟，
`stamp_age` 是当前消息时间差；最终 `age` 仍同时约束接收间隔和源时间戳。
若里程计 TF 更新明显快于导航回调，应排查接收积压，不能把旧消息改为当前时间或放宽保护阈值。

导航接收绝对位姿和速度的 `/odom` 使用 BEST_EFFORT、KEEP_LAST(1)，避免负载下按顺序重放深队列中的旧状态。
定位监视器仍保留已经处理过的位姿历史，用于与 AMCL 时间对齐；实际断流仍停止当前目标。
更新需要在结束导航并确认底盘下使能后重启导航进程，旧进程不会自动加载源码改动。
